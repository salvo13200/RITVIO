# Publish RITVIO on GitHub

The source and candidate packages can be prepared locally. No GitHub repository has been created by these scripts. Build workflows do **not** publish a release automatically, merge pull requests or request write permissions.

## 1. Create the repository from the clean export

Run `pnpm release:source` in the development workspace. `release/public-source-export.json` records the new clean directory; `release/RITVIO-public-source.zip` contains that directory as `RITVIO/`. Publish **that source tree**, not the entire development workspace. The export uses an allowlist and automated credential/path checks; review the selected content too. Excluded files must not be added later with a blanket upload of the old workspace.

Create an empty **public** GitHub repository named `RITVIO` in your personal account, without an autogenerated README or licence. Use its actual URL below. GitHub CLI is optional; ordinary Git plus browser login is sufficient. Configure Git with your own name and GitHub no-reply email before committing.

```powershell
Set-Location '<clean exported RITVIO directory>'
git init -b main
git add .
git status --short
git commit -m "Prepare RITVIO public source and release workflow"
git remote add origin https://github.com/YOUR_ACCOUNT/RITVIO.git
git push -u origin main
```

The placeholder URL is an instruction, not an active app link. No token belongs in a URL or source file. The first commit should be reviewed before pushing. Subsequent changes use a branch and pull request.

## 2. Only the owner merges

Keep yourself as the **only account with Write/Maintain/Admin access**. Public visibility grants read/fork access, not permission to change this repository. Visitors can open issues and fork-based pull requests; proposals do not change the app until you merge them. Do not invite ordinary users as collaborators. Open source licences allow downstream forks, which you do not control.

In Settings → Rules → Rulesets, import `.github/main-ruleset.json`: default branch, deletion/force-push protection, changes through pull requests, and update bypass limited to Repository Admin **for pull requests only**. With your account as the only administrator, only you can merge. Required approvals are zero deliberately: a solo maintainer cannot approve their own pull request. This rule alone does not enforce green CI for the administrator.

After CI has run once, also import `.github/main-checks-ruleset.json`. It requires `Core and web` and `Browser regression` on an up-to-date branch, with **no bypass**. The two rulesets together preserve owner-only merges and checks. Files in the repository do not activate rules by themselves: import and inspect the resulting active rules. Avoid giving bots write access or enabling automatic merge. As owner you can change repository settings; these are safeguards, not a restriction on your GitHub ownership.

Enable Issues, private vulnerability reporting and secret scanning/push protection where available. In Actions settings use read-only default token permissions, disable Actions creating/approving pull requests and require approval for external contributors' workflows. The supplied PR workflow uses `pull_request`, not `pull_request_target`, with no signing secrets.

## 3. Funding on GitHub only

Once you have your own public profile links:

```powershell
pnpm funding:configure --paypal 'https://paypal.me/YOUR_PROFILE' --coffee 'https://buymeacoffee.com/YOUR_PROFILE'
```

The command validates provider domains, writes `.github/FUNDING.yml` and updates the README's support section. It does not create payment accounts, process payments or add buttons inside the app. PayPal uses GitHub's custom funding link; Buy Me a Coffee uses its native key. Until real links are supplied, FUNDING.yml is deliberately empty and no destination is advertised. Enable **Sponsorships** in GitHub Settings → General → Features after merging the file. Review both recipient pages. Donations are optional, without feature unlocks; provider fees may apply.

## 4. Builds and signing

`CI` runs core tests, localisation, both web builds and browser regression on standard Windows GitHub-hosted runners. It has read-only repository permissions. Local checks do not prove that a workflow has run on GitHub; verify the first actual Actions run before requiring its check names.

Create a protected environment named **release**, restrict it to `main`, and require the owner's approval. Add environment secrets `ANDROID_KEYSTORE_BASE64` (the existing official `ritvio.jks` bytes encoded as Base64) and `ANDROID_KEYSTORE_PASSWORD`. Do not paste the key/password into issues or commit them. Base64 is not encryption. Keep an offline private backup too.

The manually dispatched `Build release candidate` workflow builds Windows and Android sequentially, checks JVM tests and APK alignment, validates the known official certificate, creates source archives/hash manifest and uploads a seven-day workflow artifact. It removes temporary signing material in an always-run cleanup step. Artifacts contain an explicit file list, never `.local/` or credentials. It runs only from `main` and does not create public releases. Review workflow/code changes before allowing them access to the release environment.

## 5. Create a prerelease with corresponding source

Use [the release checklist](RELEASE_CHECKLIST.md). Current native phone checks are open, so mark the initial public build as a **prerelease**, with the limitations from [release notes](RELEASE_NOTES.md). Keep Windows and Android version numbers distinct; do not reset the Android versionCode/signing key to call both apps 1.0.

From the exact reviewed source commit used to build the assets, create a tag such as `public-preview-1` and a GitHub draft release. Attach only the files listed in `release/RELEASE-MANIFEST.json`, plus `SHA256SUMS` and the manifest itself: Windows portable/installer, signed APK, RITVIO source archive, exact resolver source archive. Do not upload local logs, private design reviews, signing keys or the old build history. Never attach old binaries to a tag with changed runtime source.

Verify downloads and SHA-256, inspect source content, and test update/install from the downloaded assets before publishing the draft. Add actual relative release links to README after a release exists; no fake repository URL or expiring hosting link is embedded in the prepared README. Keep sources available as long as binaries are offered.
